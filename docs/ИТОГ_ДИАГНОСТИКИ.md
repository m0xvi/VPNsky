## Критерий приёмки — не достигнут

Исходная цель: телефон на LTE Билайн через хост `(RU)` — рабочий handshake,
внешний IP Нидерландов и загружающаяся страница.

Факт: Happ показывает «ПОДКЛЮЧЕН» с таймером, но счётчик `0 байт`,
тестовый URL по прямому IP и `https://example.com` уходят в таймаут.
Внешний IP Нидерландов **не подтверждён**. Зелёные галочки серверного чекера
и надпись «ПОДКЛЮЧЕН» рабочим трафиком не являются.

## Что доказано (больше проверять нечего)

| Область | Подтверждение |
|---|---|
| Релей RU | `tcp/443 → <NL_IP>:8443` имеет счётчик 1911 пакетов / 115 КБ; `udp/443` — реальный QUIC-обмен (36 / 46 КБ). Пакеты с телефона **доходят до релея** |
| DNAT / FORWARD / MASQUERADE / автозапуск | `--relay 13/0` после перезагрузки, 8 правил, systemd-юнит в норме |
| Путь RU → NL | tcpdump на NL: `135` пакетов от релея, `94` ответных, **`14` с данными**. Настоящий TLS ClientHello дошёл, ServerHello и сертификат ушли обратно |
| Xray / REALITY | Инбаунд `vless-reality-8443` поднят, пользователи загружены, `target` доступен с NL-ноды |
| Ключи | `pbk` и `shortId` из подписки совпадают с `state`; подписка генерируется панелью из `shortIds[0]` того же профиля |
| Панель / подписка | `HTTP 200`, 6 ссылок, хосты `(RU)` на нужных портах |

**Вывод:** серверная часть исправна полностью. Разрыв где-то на участке
«NL-нода → релей → телефон на LTE», и он не объясняется ни одной из
проверенных гипотез.

## Опровергнутые гипотезы (не повторять)

1. **DPI Билайна режет на подлёте** — опровергнуто: ClientHello `length 1024`
   дошёл до NL-ноды.
2. **Не хватает DNAT `tcp/443`** — правило добавлено, счётчик растёт; дубликат
   правила безвреден.
3. **Расхождение `shortId`** — ложное срабатывание парсера: `sid` захватывался
   вместе с `#NSky%20REALITY%20(RU)`. Исправлено в `nsky-live-probe.sh` v`.2`.
   Совет «перезапустить установщик» был ошибочным и отозван.
4. **Нода не отвечает** — `24+16=40` было обрезано лимитом `tcpdump -c 40`.
   Без лимита: 94 ответных пакета, 14 с данными.
5. **Ошибки Xray** — `grep: binary file matches` скрывал логи; после `tr -cd` +
   `grep -a` видно только WARN `StatsService/xtls-api` (шум сбора статистики,
   записи 10:42 и 13:21, к замерам отношения не имеют).
6. **MTU / MSS / rp_filter** — `TCPMSS --set-mss 1200` и `rp_filter=2`
   (`nsky-fix-last-mile.sh`) **не помогли**, подтверждено пользователем.
7. **Hysteria2 / UDP** — `U0`: UDP/443 не дошёл до ноды при выборе
   `Hysteria2 (RU)`. Протокол не заработал.
8. **Туннель был выключен** — неверная трактовка неудачного скриншота; Happ
   держал «ПОДКЛЮЧЕН».
9. **Timeweb / Билайн / DNS как единственная причина** — не подтверждено;
   таймаут был и по прямому IP.

## Простой рабочий вариант без отладки

Вместо того чтобы чинить последнюю милю каскада, предлагается **убрать каскад
из пути**:

1. **Минимум действий:** в Happ выбрать хост **без `(RU)`** — прямое
   подключение к NL-ноде (`NSky REALITY`, `8443/tcp`). NL-часть доказана
   исправной, пинг до прямых хостов на скриншотах был. Если Билайн не режет
   зарубежный IP напрямую, это заработает без релея, DNAT и REALITY-маскировки
   через российский VPS.
2. **Если нужен именно обход DPI:** заменить всю конструкцию на **AmneziaWG**
   на одном зарубежном VPS — один UDP-порт, обфускация, готовый открытый
   клиент, без панели, REALITY, подписок, коротких ID и двух серверов. Это
   убирает сразу все проверенные точки отказа. Подготовить такой конфиг
   должен ассистент, не пользователь.

Ни один из этих вариантов не требует от пользователя новых замеров, логов или
выводов команд.

- Общаться по-русски, по пунктам, коротко. Не превращать пользователя в
  отладчика.
- Не просить «ещё один вывод» без явной просьбы с его стороны.
- Не выдавать непроверенную причину за факт. Причина здесь **не установлена**.
- Только плейсхолдеры: `<DOMAIN>`, `<NL_IP>`, `<RU_IP>`, `<SUB_SECRET>`,
  `<shortUuid>`, `<ADMIN_PASS>`. Live-выводы содержали реальные домены, IP,
  UUID, имена контейнеров и VPS — в чат и коммиты их не переносить.
- Production-домен из старой записки не трогать. Перед изменениями на сервере —
  точка восстановления.
