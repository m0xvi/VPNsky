## 2. Что меняет ответ «нужен выход за рубеж»

### 2.1. Появляется юридический трек, и он важнее технического

Раз цель — доступ к зарубежным ресурсам, у вас есть **официальный** путь, а не только обход
ТСПУ. По данным РКН на 22.04.2026: доступ к зарубежным ресурсам предоставлен **57 тыс.
IP-адресов и подсетей 1730 организаций**; заявки принимает ЦМУ ССОП (ГРЧЦ) на
**white_list@cmu.gov.ru**.

Что указать в заявлении (по разъяснениям РКН):

1. наименование организации и ИНН;
2. используемый протокол подключения;
3. IP-адрес источника подключения (при возможности);
4. IP-адрес назначения подключения;
5. цель использования соединения;
6. контакты ответственного представителя;
7. дополнительные комментарии при необходимости.

**Рекомендация:** подать заявление **параллельно** с разработкой, сразу как появится
постоянный IP зарубежного exit-узла. Причины:
- рассмотрение занимает время, а не дни; лучше, чтобы к пилоту адреса уже были в списке;
- включённый IP снимает большую часть проблем с ТСПУ — то есть уменьшает объём работы
  по «протокольной гонке»;
- это законный режим для корпоративного использования, а не серая зона.

Что нужно понимать про риски этого пути:
- включение в список — не гарантия навсегда: IP можно исключить;
- заявление подразумевает раскрытие регулятору IP и протоколов — это нормально для
  корпоративного канала, но должно быть осознанным решением;
- 100% гарантии, что одобрят, нет.

**Техническое следствие:** архитектура должна работать в двух режимах — «адрес в белом
списке» (можно всё) и «адреса нет» (нужны устойчивые транспорты). Поэтому выбор
REALITY + XHTTP + Hysteria2 остаётся, но перестаёт быть единственной опорой.

### 2.2. Exit-узел и control plane нужно разнести

Это самое важное архитектурное изменение относительно базового документа.

| Что | Где размещать | Почему |
|---|---|---|
| **Control plane** (API, БД, админка) | РФ или отдельный хост, **не на IP exit-узла** | Если exit заблокируют, сотрудники должны иметь возможность получить новый конфиг и переключиться |
| **Exit-узлы** | За рубежом, 1+ | сам туннель |
| **Резервный канал управления** | второй домен/IP | на случай блокировки домена |

Если control plane стоит на том же IP, что и VPN, то блокировка IP означает: туннель упал
**и** обновление конфигурации не приходит. Продукт превращается в «звоните в поддержку».
Именно этого мы избегаем.

### 2.3. Несколько exit-узлов — с первого дня в модели данных

Даже если физически будет один сервер, схема должна поддерживать N:

```
nodes(id, name, country, endpoint_host, weight, status, created_at)
node_credentials(node_id, kind, params_encrypted)
device_node_assignments(device_id, node_id, priority)
```

Клиент получает список узлов с приоритетами и сам переключается. Добавление второго узла —
операция в админке, а не пересборка приложения. Это же снимает часть рисков одного VPS,
о которых предупреждал архив.

### 2.4. Сплит-туннель становится практической необходимостью

При зарубежном exit «весь трафик через VPN» означает, что запрос к `gosuslugi.ru` или
`nalog.ru` идёт в Европу и обратно. Последствия: +100–200 мс, съеденный трафик, а часть
российских сервисов вообще отказывает иностранным IP (банки, госуслуги, некоторые
маркетплейсы).

Рекомендуемая политика по умолчанию:

| Категория | Маршрут |
|---|---|
| Заблокированные и иностранные ресурсы | через туннель |
| Российские ресурсы (`geoip:ru`, `geosite:category-ru`) | напрямую |
| Локальная сеть, принтеры, NAS | напрямую |
| DNS | через туннель (или DoH), без утечек по RU-запросам |
| Всё остальное | через туннель |

При этом политика должна приходить с сервера и меняться без переустановки приложения —
именно это и есть та автоматизация, ради которой всё затевается. Плюс отдельный
«параноидальный» режим «весь трафик», если понадобится.

**Нужно ваше решение:** согласны ли на сплит по умолчанию, или требование «всё через VPN»
жёсткое. Мой совет — сплит по умолчанию + возможность включить полный туннель.

### 2.5. География exit-узла

Что учитывать при выборе страны (пока не выбираем окончательно):
- **латентность** до Калининграда: Финляндия/Швеция/Германия/Польша дают 20–60 мс,
  Нидерланды — 40–70 мс, Турция — 60–90 мс;
- **отношение к такому трафику** у хостинг-провайдера: дешёвые «VPN-friendly» провайдеры
  часто попадают в блокировки целыми подсетями;
- **репутация подсети**: если IP уже в чёрных списках, часть сервисов будет отказывать
  (капчи, «подозрительный трафик»);
- **юрисдикция хранения** — для корпоративного трафика имеет значение.

Практика: 2 узла в разных странах/провайдерах дешевле, чем один «идеальный», и даёт
устойчивость. На тестовом этапе достаточно одного.

## 3. Что остаётся без изменений

- Ядро — **Xray-core** (MPL-2.0) на сервере и в клиенте, с `libXray` для мобильных/десктопа.
- sing-box / Karing / Hiddify как основа — **нельзя** (GPLv3 + доп. условия, закрытый продукт).
- UI — Flutter, две сборки (сотрудник / админ), разные пакеты и ключи подписи.
- Control plane — свой сервис на Go, без панелей 3x-ui/Marzban/Remnawave (AGPL).
- Индивидуальные учётные данные на устройство: Xray API (`inbound_user_add/remove`) +
  Hysteria2 `auth.type: http` → ваш эндпоинт.
- «Подключено» показывается только после реального запроса через туннель.
- iOS требует платного Apple Developer Program (бесплатный аккаунт VPN не даёт).

## 5. Скорректированный план

| Этап | Что делаем | Зависит от |
|---|---|---|
| **0** | Ответы на §4 (1–3), заявка в ЦМУ ССОП, выбор провайдера | вы |
| **1** | Тестовый VPS за рубежом: Xray (REALITY + XHTTP) + hysteria-server + отдельный control-plane хост; ручные замеры с Windows/Android в Wi-Fi и LTE | §4.1–4.2 |
| **2** | Скелет репозитория: сборка Xray из исходников в Actions, `versions.env`, SBOM, notices | — (можно параллельно) |
| **3** | Ядро клиента: `libXray` + загрузка/подпись/откат конфигурации + TUN на Windows | этап 1 |
| **4** | Control plane MVP: устройства, токены, узлы, выдача, отзыв, аудит | этап 1 |
| **5** | UI Windows для сотрудника (один экран) | этапы 3–4 |
| **6** | Админка Windows/Android | этап 4 |
| **7** | Пилот 5–10 человек | этапы 5–6 |
| **8** | Android для сотрудников, затем iOS | этап 7 |

Этап 2 можно начать не дожидаясь сервера — это чистая работа с репозиторием и CI.
