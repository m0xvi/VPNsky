# Архитектура продукта и политика безопасности

## Продукт

Интерфейс сотрудника: первая активация и главная кнопка «Подключить / Отключить»; ясные состояния «Подключено», «Подключаемся», «Восстанавливаем соединение», «Нет доступа», «Действие администратора». Справка и служебная диагностика — отдельно; не показывать сотруднику ключи и десятки протокольных переключателей по умолчанию. Доступность интерфейса, русский язык, читаемый текст и работа на маленьком экране. Никакой недостоверной надписи «защищено», если тест через туннель не пройден.

Поддержать Windows 10/11 x64 сначала; минимальную сборку Windows, архитектуру ARM64/32-bit и права сотрудников согласовать. Затем Android и iOS: общая бизнес-логика и UI предпочтительны, но системные VPN-интеграции останутся платформенными. Ядро и протоколы не переписывать.

## Разделение слоёв

- Клиентский UI + состояния подключения.
- Адаптер ядра/движка с явным отображением версии и возможностей. Управление конфигурацией, запуск/остановка, безопасная обработка ошибок и тестирование.
- Платформенные модули: Windows TUN и права, Android VpnService, iOS Network Extension. Системный HTTP/SOCKS-прокси Windows не покрывает весь трафик.
- Центр управления на существующем VPS: идентичности пользователей/устройств, политики, выдача конфигураций, версии, аудит.
- Бот — административный интерфейс центра, а не отдельный конкурирующий источник правды.
- VPN data plane: действующие Xray и Hysteria2; смена возможна только в отдельном согласованном плане. Панель, серверы и ядра не считать взаимозаменяемыми.

Один VPS = одна точка отказа. Клиентские протоколы на разных транспортах могут переживать некоторые ограничения по-разному, но не заменяют второй независимый сервер/адрес. Его добавление противоречит текущим ограничениям и требует нового решения пользователя.

## Активация, учётные данные и удалённое управление

1. Администратор создаёт устройство. В перспективе: уникальный ID и отдельные VPN-учётные данные на устройство. Для существующих Hysteria-пользователей сначала проверить тип авторизации; перевод с общего пароля требует отдельной миграции и теста старых клиентов.
2. Бот выдаёт персональный **одноразовый случайный** токен активации / QR. Сервер проверяет срок 10 минут и уже выполненное использование; атомарно помечает его использованным. Не хранить дольше необходимого, исключить попадание в access-логи, Referer, аналитику и кеш; HTTPS и безопасная страница без сторонних ресурсов. Не считать такой механизм уже реализованным в нынешней странице.
3. При активации клиент получает отдельный токен устройства и конфигурацию. Токены хранить защищённо: Windows Credential Manager/DPAPI, Android Keystore, iOS Keychain — выбрать на этапе разработки; секрет может быть скопирован при компрометации устройства, гарантии аппаратной привязки нет.
4. Клиент аутентифицируется к персональному API, получает версии/политики с нормальной проверкой TLS, проверяет схему и совместимость, применяет с возможностью отката. Добавить подпись конфигурации и управляемую ротацию ключа подписи после проектирования; подпись защищает подлинность, но не скрывает данные. Не принимать исполняемые команды сервера как код и не разрешать произвольные скрипты.
5. Сохранять последнюю **корректно применённую** конфигурацию на устройстве шифрованием/платформенным хранилищем. Атомарно включать новую только после валидации и локальной проверки ядра; при ошибке не уничтожать старую.
6. Администратор может отозвать **две независимые сущности**: право получать обновления и серверные VPN-учётные данные. Иначе скопированный старый ключ продолжит работать. Задать ожидаемое поведение действующих сессий и проверять его на практике; новые учётные данные на устройство для обоих протоколов — цель будущей системы, не факт текущей.

Режим выдачи: ссылки на 10 минут не равны постоянно действующему URL подписки. Если первоначально используется существующее неподдельное приложение, защищённая подписка может быть отдельным bearer-секретом, но её действие и возможность управления зависят от формата и клиента; такой временный компромисс не равен будущему управляемому API.

## Надёжность туннеля

- По умолчанию весь трафик через TUN/VPN и DNS через контролируемый путь. Отдельно решить IPv6, локальную сеть, корпоративные маршруты, разрешение имён, captive portal и конфликт с другими VPN. Полного отсутствия утечек не обещать, пока не проверены все перечисленные сценарии.
- При обрыве — контролируемое переподключение с backoff и jitter. Выбор VLESS ↔ Hysteria2 по реальной периодической проверке через соответствующий туннель, пороги и задержка возврата, чтобы не флапать. Проверку не считать гарантией работы любого сайта.
- Kill switch / fail-closed — отдельная согласуемая политика. Включать и рекламировать её только после платформенных тестов, в том числе перезапуска и падения приложения, с безопасным восстановлением интернета администратором. Если он не реализован, честно предупреждать о возможном выходе напрямую при падении VPN.
- Продумать безопасное начальное получение конфигурации, DNS и доступ к control plane, когда туннель не поднят. При строгом kill switch исключение для endpoint опасно и платформенно различается; фиксировать явную политику и проверять без утечек.
- Встроенные статистика/heartbeat и push не являются мгновенной доставкой или доказательством онлайн-состояния: фоновые ограничения и интернет могут мешать. Последняя активность должна быть помечена временем и не считать отсутствие ответа отключением VPN.

## Администрирование и данные

- Доступ в чат-группу подтверждён прежним ботом по `cid` и `/bind` был отключён. Но доступ по чату не проверяет конкретного администратора. Для нового control plane использовать авторизацию по Telegram user ID + разрешённый chat ID и логирование административных операций; не вводить PIN. Учесть возможности и ограничения бота в группе и Telegram 2FA как отдельную организационную меру.
- Случайные токены — персональные, HTTPS, не отправлять в общую группу больше секретов, чем необходимо. Уточнить безопасный канал выдачи сотрудникам; группа администраторов всё равно видит то, что в неё отправлено.
- В логах — тип операции, время, обезличенный ID/псевдоним, итог, обобщённая категория ошибок. Ни UUID, паролей, IP клиентов, сайтов, ссылок/токенов, query string, полного конфига. Информация о сотрудниках и диагностике — персональные/корпоративные данные; определить consent/политику retention. Минимизировать клиентскую диагностику и отправлять только при согласованной политике.
- Минимальные права служб, локальная административная привязка API, backup базы и конфигов с шифрованием, проверка восстановления, audit; не размещать бэкапы и секреты в GitHub.
- Никаких секретов в Actions-логах и артефактах, issue, скриншотах, архивах чата. Отдельные стадии local/fake/test/prod; production доступ не нужен для обычного CI.

## Безопасная смена действующей серверной схемы

В дальнейшем: инвентаризация read-only → карта владельцев конфигураций, портов, watchdog → согласованный план и окно → защищённый проверяемый backup и инструкция восстановления → тестовая клиентская группа/изолированный контур на том же VPS без конфликтов портов → проверка конфигов и соединений → постепенный перенос → наблюдение → явное решение об удалении старого. Новая панель не должна переписывать чужой Xray-конфиг или одновременно с текущим ботом управлять одним сервисом. Если переключение одного 443 требует простоя, обозначить его заранее. Любые модификации production — только после разрешения пользователя.
