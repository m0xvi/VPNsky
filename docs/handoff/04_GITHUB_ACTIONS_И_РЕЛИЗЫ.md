# GitHub и релизы через GitHub Actions

## Статус

В этой сессии коннектор GitHub вернул `unsupported`; проверены публичные источники через интернет, но подключения к аккаунту, репозитория, Actions или релизов не создано. В следующей сессии выяснить, доступен ли там коннектор, а при отсутствии — возможен ли обычный Git/`gh` через безопасную авторизацию пользователя. Не предполагать доступ и не просить прислать PAT в чат. Можно подготовить код локально и дать пользователю инструкции для браузера/CLI.

## Выбор репозитория и распространения

- Выяснить владелец/организация GitHub, желаемый URL, private/public, права агента, может ли пользователь принимать PR и включать Actions.
- Для модифицированного upstream проверить, требуется ли именно GitHub fork и какая видимость исходников подходит с точки зрения лицензионных условий. Не записывать туда архив этого задания, данные VPS и пользователей.
- Private GitHub Releases обычно доступны только имеющим права на репозиторий. Нельзя рассчитывать, что сотрудники с обычной ссылкой скачают их без авторизации. Варианты — ограниченные аккаунты GitHub, согласованное корпоративное распространение через MDM/хранилище или отдельный **одобренный** публичный канал бинарников. Для последнего отдельно выполнить обязательства исходников и лицензий. Это не необходимость второго VPS.
- Защитить `main` и release-теги, требовать проверки/ревью и при наличии возможностей плана — подтверждение среды release. Допуск к workflow и изменение release-политик ограничить. Иммутабельность релизов включать, если доступна.

## Рекомендуемый pipeline: Windows первым

Сначала выбрать и зафиксировать upstream commit/tag, проверить лицензии, субмодули, способ извлечения или сборки ядра, файлы проекта и фактический способ сборки. Workflow писать **под проверенную структуру**, а не копировать абстрактный YAML. Если кандидат Flutter, официальная среда Windows использует Visual Studio C++ workload и `flutter build windows`; конкретные команды и зависимости проверяются на выбранной версии проекта.

### CI на PR и main — `contents: read`

1. GitHub-hosted `windows` runner; фиксированная версия/хэш SDK и зависимостей, проверка lockfiles. Зафиксировать также реальные commit SHA используемых Actions и их проверенный источник.
2. Получить исходники и подтверждённые субмодули; не выполнять произвольный remote `curl | bash`. Полученные бинарные ядра проверять по доверенному хэшу/подписи, либо воспроизводимо собрать из исходников. Учитывать transitive dependencies и источник хэша: хэш, взятый из того же ненадёжного места, не аутентифицирует пакет.
3. Анализ/тесты, сборка `release`, проверка нужных бинарников, архитектуры, assets, лицензий, smoke-запуск там, где возможен, статическая проверка секретов. Платформенные TUN/маршруты и подключение на hosted runner не заменяют ручной сетевой тест.
4. Upload Actions artifact для CI (не production-релиз); явные failure при отсутствии файла. Артефакт должен содержать все DLL, ядро, assets, лицензии, файлы, необходимые для запуска. ZIP не всегда является установщиком — назвать его точно.
5. Фиксировать версию UI и ядра, commit, версию схемы, reproducibility/input manifest. Сборка на GitHub Actions не гарантирует ни воспроизводимость бит-в-бит, ни безопасность без проверки.

### Публикация тестового релиза

- Только после успешных checks: защищённый tag (например, `v0.1.0-test.1`), предварительное одобрение владельца, привязка к проверенному commit и контроль источника тега.
- Выделенный job/environment с минимальным `contents: write` для GitHub Release, без неиспользуемых разрешений; по возможности артефакт из предыдущего проверенного job, а не новая произвольная сборка. Никогда не предоставлять подписывающие секреты неподтверждённому PR/fork.
- Создать **draft или prerelease** Windows x64; добавить ZIP или установщик и `SHA256SUMS.txt`, описать изменения, ОС, версию ядра и ограничения, состояние подписи, инструкцию обратной связи и удаления. Собранные сертификаты/секреты не публиковать.
- Верифицировать скачанный release asset и checksum, скачать на чистую тестовую Windows, проверить запуск и сценарии из `05_WINDOWS_MVP_И_ТЕСТЫ.md`. Проход CI ≠ рабочее VPN-подключение.
- Сумма из того же релиза помогает выявить случайное повреждение, но не защищает от атакующего, контролирующего и файл, и checksum. Применять Windows code signing; по возможности использовать проверяемые attestations и SBOM, документировать отдельно ограничения.
- До production уточнить сертификат Authenticode, подписывание всех требуемых исполняемых файлов/инсталлятора, timestamp и проверку подписи. Неподписанные тестовые сборки Windows могут предупреждать SmartScreen и не должны поставляться как корпоративный production; не инструктировать пользователей отключать защиту.

GitHub Actions не предоставляет автоматическое волшебное подписание: Windows сертификат и ключ, доступный и допустимый способ использования, организация, разрешения и бюджет зависят от выбранной модели. Защитить ключ и release environment, не коммитить его.

## Android — после Windows

- Android build job на поддерживаемом runner с согласованными версиями Flutter/JDK/Android SDK/NDK и открытого ядра. Сначала тестовый signed APK; production ключ подписи отдельно и защищённо. APK/AAB, версия, fingerprint сертификата, license notices и checksum — документировать.
- Не публиковать keystore и пароли; защищённое хранение и backup с процедурой ротации/потери. Test key и production key разделить, не обещать обновление одной сборки поверх другой при разных ключах.
- Проверить VPN permission, маршрут всего трафика, DNS/IPv6, смену сетей и battery restrictions на реальных устройствах. CI-эмулятор полезен для части тестов, но не подтверждает корректность реального мобильного VPN.

## iOS — после Android, архитектурный gate сейчас

- Проверить годность open-source лицензий для выбранного способа распространения и Apple. Создать/app ID, Network Extension capability/entitlements, profiles для приложения и расширения; нужен Apple Developer и соответствующая возможность, Xcode/macOS. Доступность аккаунта/прав заранее не подтверждена.
- GitHub-hosted macOS runner может собрать/подписать при наличии надёжно предоставленных сертификатов, private key, provisioning profiles и App Store Connect API-доступа. Выбор безопасного signing-процесса — после выяснения учётной записи. Не публиковать .p12, профили и ключи.
- TestFlight — через App Store Connect, с подписью и правилами Apple, не обычный публичный APK-аналог. Для публичного App Store у Apple правило 5.4 для VPN-приложений включает организационный аккаунт и требования приватности; региональные и юридические ограничения проверить отдельно.
- На реальных iPhone испытать установку, разрешение VPN, переподключение, переключение Wi‑Fi/сотовая и фоновое поведение. GitHub workflow и собранный IPA сами по себе не подтверждают реальный VPN.

## Защита CI/CD

- Никаких VPS production-ключей, UUID, подписок и данных реальных сотрудников в GitHub, test fixtures, Action artifacts, сборках, логах и release notes. Фиктивные значения обозначить явно и сгенерировать локально.
- GitHub token: `contents: read` по умолчанию, `contents: write` только в release-job. `pull_request_target`, непроверенный код из PR, небезопасные интерполяции и self-hosted runners с секретами не смешивать.
- Third-party actions pin к проверенным полным commit SHA, обновлять контролируемо; job isolation, approve environments, audit и branch/tag protections. Кеш не использовать для хранения секретов, не доверять кешу untrusted PR.
- Дополнительная аттестация provenance/SBOM полезна, но её доступность зависит от видимости репозитория и плана GitHub; она не гарантирует отсутствие вредоносного кода. Все изменения workflows требуют review.
- GitHub подписка/лимиты, минуты Windows/macOS, квоты и региональная доступность проверяются на аккаунте пользователя, не обещать бесплатную бесконечную сборку.

Пока в архиве нет файла `.github/workflows`: без выбранной кодовой базы он был бы фиктивным или потенциально опасным. Следующий агент должен создать и **реально запустить** workflow после доступа к репозиторию либо честно передать его для самостоятельного запуска, если доступа нет.
