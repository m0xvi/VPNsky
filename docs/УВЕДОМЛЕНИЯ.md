# Уведомления сотрудникам: что реально можно, а что нет

Дата: **5 ноября 2026**. Проверено по документации Happ и Remnawave.

Фича нужная (идея правильная), но важно понимать одну вещь: **с готовыми клиентами сотрудник
не «их» приложение, и push-уведомления вы туда не вставите.** Всё, что панель может передать
клиенту, — это HTTP-заголовки ответа подписки и текст внутри неё. Ниже — что из этого
получается.

---

## 1. Что сейчас возможно без своего клиента

Remnawave отдаёт клиенту подписку вместе с заголовками, которые читает приложение.
У Happ это документированные параметры управления (`happ.su/dev-docs/app-management`):

| Заголовок | Что даёт сотруднику | Ограничения |
|---|---|---|
| `announce` | текст-объявление в приложении (plain или base64) | **до 200 символов**; показывается при обновлении подписки |
| `profile-title` | название профиля в приложении | до 25 символов |
| `subscription-userinfo` | строка «трафик / лимит / дата окончания» | это уже работает, просто счётчики |
| `support-url` | кнопка «поддержка» в приложении | ссылка |
| `profile-web-page-url` | кнопка на вашу страницу подписки | ссылка |
| `profile-update-interval` | как часто приложение тянет подписку | в часах |
| `providerid` | связка подписки с аккаунтом happ-proxy.com → расширенная статистика | требует регистрации на happ-proxy.com |

Плюс в Happ есть **расширенные параметры**, для которых нужен тот самый `providerid`:
подписка (`sub-info`) и системное уведомление об окончании (`sub-expire`), плюс
**push-уведомления и команды удалённого управления** через API happ-proxy.com.

Отдельно у Happ есть автоматические напоминания: за 3 дня до окончания подписки, раз в день —
но это про срок, а не про «VPN недоступен».

### Вывод по трём сценариям из вашей идеи

| Сценарий | Возможно? | Как |
|---|---|---|
| «Плановое обслуживание 22:00–23:00» | **Да** | `announce` — но увидит только тот, кто в этот момент обновляет подписку. Ограничение 200 символов |
| «VPN сейчас недоступен, мы знаем и чиним» | **Частично** | Через `announce` при следующем обновлении подписки. Мгновенного пуша не будет. Если туннель лежит, приложение может вообще не дотянуться до подписки |
| «Всё восстановлено» | **Частично** | Тот же `announce`; прочитают, когда обновят подписку |
| **Мгновенный push «VPN не работает»** | **Нет** (без своего клиента) | Нужно своё приложение с push-токенами — но см. §3: это и не нужно |

## 2. Что важнее уведомлений: другой канал доставки конфигурации

Ключевая проблема: если сломался VPN, **подписка сотруднику тоже может быть недоступна**
(например, заблокирован IP ноды и домена подписки). Тогда любой `announce` — бесполезен,
он едет по тому же сломанному пути.

Поэтому в архитектуре уже заложено: **панель и страница подписки живут на отдельном хосте/IP,
не на IP ноды**. Тогда:

```
VPN-нода упала / заблокирована  →  подписка (другой хост) жива
                                →  приложение обновляет подписку
                                →  получает announce + новый конфиг
                                →  сотрудник видит сообщение и новые серверы
```

Это и есть «уведомление» в реальной жизни, и оно работает без всякого push.

## 3. Почему push-уведомления — плохая идея именно здесь

1. **Технически это не «уведомление», а болезнь.** Приложение с постоянным каналом
   до серверу = второй постоянный коннект, батарея, разрешения, «почему приложение
   всегда в сети». Для VPN-клиента это отдельный класс проблем.
2. **Готовые клиенты это не поддерживают** (кроме Happ Enterprise-тарифа через
   happ-proxy.com — платно, с регистрацией у стороннего сервиса).
3. **Свой клиент ради push — несоразмерно.** Свой клиент нужен ради UX и брендинга,
   а не ради уведомлений.

Практичная альтернатива, если нужны гарантированные сообщения:
- **страница статуса** (`status.домен.ру`) — простой статичный хостинг, обновляется вручную
  или скриптом при инциденте;
- ссылка на неё в `announce` и в `support-url`;
- **корпоративный канал, который уже есть** — почта, корпоративный мессенджер, доска
  объявлений. Это не «Telegram-бот для управления», а просто канал оповещения.

## 4. Как реализовать announce в Remnawave (когда дойдём)

1. Панель → **Subscription → Settings → Additional Response Headers**.
2. Добавить заголовок `announce`. Значение — текст, при необходимости base64
   (`rwEncodeBase64:...`). Учтите лимит 200 символов.
3. Текст можно шаблонизировать переменными панели, например
   `{{STATUS:ACTIVE=✅ Работает|EXPIRED=Просрочена}}` (см. `PAGE_RESPONSE_HEADERS`).
4. Быстрое «включить/выключить объявление» — это правка одного заголовка в панели.
   Проверить на пилоте: когда приложение подхватывает новый announce (при обновлении подписки,
   по `profile-update-interval`).

Плюс настройки страницы подписки: брендинг, логотип, `support-url` — чтобы сотрудник видел
«куда писать», а не искал.

## 5. Что можно сделать в админ-приложении (ваша вторая часть идеи)

Админ узнаёт о проблеме раньше сотрудников — это делается **без своего клиента**:

- **Готовые Android-админки к Remnawave** уже есть: `yniyniyni/FreedomWave` (KMP, исходники,
  EUPL-1.2, русский язык, биометрия, виджет), `Case211/remnawave-android-release` (APK),
  `samur005/RemnaAdmin-releases` (APK). Умеют ноды, пользователей, хосты, часть —
  уведомления о падении нод.
- Свой Windows-админ: PWA панели (`msedge --app=...`) или, позже, свой клиент к API
  (есть официальные SDK: Go, Python, TypeScript).
- **Мониторинг нод**: `xray-checker` + Prometheus-метрики панели/ноды → алерт в тот канал,
  который у вас уже есть. Это дешевле и надёжнее, чем push в клиент.

Итого цепочка: мониторинг заметил проблему → админ получает сигнал → админ жмёт кнопку
«объявление» → клиенты при обновлении подписки видят текст → при восстановлении текст
меняется/снимается.

## 6. Что записываем как решение

| Пункт | Решение |
|---|---|
| Telegram-бот | **Исключён.** Управление — админ-приложение (Android готовое / Windows PWA) |
| Сервер | **Готовое решение** — Remnawave (панель + ноды), без своего control plane |
| Уведомления сотрудникам | **Future feature.** Этап 1: `announce` + страница статуса + `support-url`. Этап 2 (если понадобится): своё приложение с push — только вместе со своим клиентом, не раньше |
| Мониторинг | Обязателен с первого дня: иначе «уведомлять» будет не о чем |
