# Проверка каскада и первая работа с панелью

Дата: 6 ноября 2026. Документ про **текущее** состояние: панель Remnawave стоит
на нидерландском VPS, русский VPS работает релеем, на клиентах каскад ещё не
проверялся.

Задача каскада — обойти мобильные блокировки (в первую очередь Билайн): сотрудник
подключается к **российскому IP**, а тот на уровне ядра пересылает пакеты на
нидерландскую ноду. Зарубежного IP в соединении клиент не видит.

```
телефон (Билайн/LTE)
   → русский VPS: DNAT 8443/tcp, 2053/tcp, 443/udp
      → нидерландская нода: Xray REALITY / XHTTP / Hysteria2
         → интернет (выход в NL)
```

Релей ничего не расшифровывает: TLS клиента идёт до NL-ноды целиком. Панель и
страница подписки через релей **не идут** — они живут на зарубежном домене.

---

## 0. Важно: чего НЕ может проверить этот репозиторий

Из среды разработки нет SSH на ваши VPS и нет доступа к произвольным хостам в
интернете. Поэтому «проверить каскад» здесь = проверить код и конфигурацию,
дать скрипт для серверов и сценарий для телефона. Живые проверки делаете вы —
команды ниже. Скрипт `deploy/nsky-cascade-check.sh` **только читает** состояние,
ничего не меняет.

Что уже проверено локально (моки + `bash -n`): `nsky-relay.sh` создаёт ровно
8 правил, повторный запуск их не дублирует, `--remove` снимает все, сгенерированный
`/opt/nsky-relay/apply.sh` синтаксически корректен; новый чекер на синтетической
подписке из 6 ссылок находит все `(RU)`-хосты и ловит ошибки адреса/инбаунда.

**Слабое место старой диагностики:** `nsky-install.sh --check` проверяет каскад
только одним TCP-коннектом `NL → RU → NL` на порт 8443 и подписывает его как
«RU→NL». Он не проверяет 2053/tcp, 443/udp, не смотрит, есть ли в подписке хосты
`(RU)`, и не заменяет тест с телефона. Пользоваться можно, но верить этой одной
строке как «каскад работает» нельзя.

## 1. Перед любыми действиями: SUB_SECRET

После прошлого `--wipe` секрет подписки мог остаться только в Caddyfile, а не в
`/opt/nsky/install-state.env`. Пока строки `SUB_SECRET=` в state нет, **любой**
следующий запуск установщика сгенерирует новый секрет и убьёт уже розданные
ссылки. Новый чекер это проверяет первым делом.

Проверка (на NL-сервере):

```
grep '^SUB_SECRET=' /opt/nsky/install-state.env
```

Если строка есть — ничего делать не надо. Если пусто, сначала бэкап, потом фикс:

```
cp /opt/nsky/install-state.env /opt/nsky/backups/install-state.manual.env
SUB_SECRET=$(grep -oP '(?<=handle /)[^/]+' /etc/caddy/Caddyfile | head -1)
sed -i '/^SUB_SECRET=/d' /opt/nsky/install-state.env
echo "SUB_SECRET=$SUB_SECRET" >> /opt/nsky/install-state.env
grep '^SUB_SECRET=' /opt/nsky/install-state.env
```

## 2. Русский VPS: правила релея

Скачайте чекер (SHA коммита указан в конце документа) и запустите в режиме
`--relay`:

```
cd /root
curl -fsSL -o nsky-cascade-check.sh https://raw.githubusercontent.com/m0xvi/VPNsky/COMMIT_SHA/deploy/nsky-cascade-check.sh
bash nsky-cascade-check.sh --relay
```

Что он покажет: `ip_forward=1`, включён ли `nsky-relay.service`, все 8 правил
(3 DNAT, MASQUERADE, 4 FORWARD), счётчики пакетов, порядок цепочки FORWARD,
состояние ufw, нет ли на релее своих слушателей на 8443/2053/443.

Дополнительно можно вызвать встроенный статус самого релея:

```
bash /root/nsky-relay.sh --status
```

Если чекер ругается на отсутствующие правила — перепримените релей (он
идемпотентен, существующий конфиг не ломает):

```
bash /root/nsky-relay.sh <IP_нидерландского_сервера>
```

Обратите внимание на счётчики `iptables -t nat -L PREROUTING -nv`: если после
попытки подключения с телефона цифры не растут, пакеты до релея не доходят —
проблема до каскада (Билайн режет сам IP/порт, либо не открыт ufw у хостера).

## 3. Нидерландский VPS: подписка и путь трафика

```
cd /root
curl -fsSL -o nsky-cascade-check.sh https://raw.githubusercontent.com/m0xvi/VPNsky/COMMIT_SHA/deploy/nsky-cascade-check.sh
bash nsky-cascade-check.sh
```

Проверяется:

| Что | Зачем |
|---|---|
| `SUB_SECRET`, `CASCADE_IP`, токен, тестовая подписка в state | чтобы ссылки не «поехали» при следующем обновлении |
| Публичная ссылка отвечает через Caddy | секретный путь `/…/api/sub/…` работает |
| В подписке 6 ссылок (или 4 без Hysteria2) | хосты `(RU)` реально созданы панелью |
| Адрес `(RU)`-ссылок = IP русского VPS | каскад указывает туда, куда нужно |
| Порт и SNI у `(RU)` | 8443/2053 с `www.microsoft.com`, 443/udp с доменом NL |
| Пара «прямой / (RU)» отличается **только адресом** | оба хоста привязаны к одному инбаунду, ключи REALITY совпадают |
| TLS-рукопожатие на `RU_IP:8443` и `:2053` с нужным SNI | рукопожатие реально доходит до REALITY-ноды, а не просто «порт открыт» |
| UDP/443 возвращается на NL-ноду | DNAT для Hysteria2 работает (нужен `tcpdump`) |
| `ss`, `ufw` | нода слушает 8443/2053/443udp, порты открыты |

Для сравнения можно запустить и старую диагностику (ничего не меняет):

```
bash /root/nsky-install.sh <домен> <email> --check
```

Частые причины `✗`:

| Симптом | Что делать |
|---|---|
| Нет хостов `(RU)` в подписке | `bash nsky-install.sh <домен> <email> --cascade <IP_русского_VPS>` |
| `(RU)` ведёт не на тот IP | тот же запуск с правильным `--cascade`, затем обновить подписку в клиенте |
| Отличаются не только адресом | хосты привязаны к разным инбаундам; перезапустить установщик без `--wipe` |
| TLS через RU не идёт, а напрямую на `127.0.0.1:8443` идёт | DNAT/форвард/ufw на русском VPS (раздел 2) |
| TLS нет нигде | проверьте доступность `www.microsoft.com:443` с NL-ноды (это `target` REALITY); к каскаду может не относиться |
| UDP/443 не вернулся | ufw на обоих VPS, `iptables` правило 443/udp, либо провайдер режет UDP |
| Публичная ссылка 404 | `SUB_SECRET` в state не совпадает с сегментом в `/etc/caddy/Caddyfile` |

Если `tcpdump` не установлен, UDP-проверка пропускается — её заменит телефон.

## 4. Главная проверка: телефон на Билайне (не Wi-Fi)

Это и есть тот тест, ради которого всё затевалось. Серверная диагностика его
не заменяет.

1. **На Wi-Fi** откройте страницу подписки или добавьте ссылку в Happ / v2rayTun /
   Hiddify. Обновите подписку. Должно появиться 6 серверов: `NSky REALITY`,
   `NSky XHTTP`, `NSky Hysteria2` и те же три с пометкой **`(RU)`**.
2. **Вручную выберите `NSky REALITY (RU)`**. Автовыбор почти всегда возьмёт
   прямой зарубежный сервер — на Билайне он и не подключится.
3. Выключите Wi-Fi, включите мобильный интернет Билайн, убедитесь, что другой
   VPN/«защищённый DNS» выключен.
4. Нажмите «Подключить». Дайте 10–15 секунд.
5. Откройте `https://2ip.ru` или `https://ipinfo.io` — страна/IP должны быть
   нидерландскими. Это значит, что трафик прошёл `RU → NL`.
6. Проверьте счётчики на русском VPS: `iptables -t nat -L PREROUTING -nv` —
   на 8443 должны появиться пакеты.
7. Если REALITY (RU) не поднялся — по очереди `NSky XHTTP (RU)` →
   `NSky Hysteria2 (RU)` → для сравнения прямой `NSky REALITY`. Запишите, какой
   протокол и какая ошибка.

**Важный нюанс именно для Билайна:** ссылка подписки и панель живут на
зарубежном домене (`443/tcp` NL-сервера), через релей они не пробрасываются.
Обновляйте подписку заранее, по Wi-Fi. Если Happ на LTE не может обновить
подписку, но туннель при этом поднимается — это не поломка каскада: конфиг уже
в кэше. Если же Билайн режет вообще весь зарубежный HTTPS, понадобится отдельная
доработка — проксировать `443/tcp` подписки через русский VPS (сейчас не
реализовано, порт свободен: релей занимает только `443/udp`).

Ещё нюанс: у `Hysteria2 (RU)` в SNI стоит ваш зарубежный домен, а у
`REALITY (RU)` / `XHTTP (RU)` — `www.microsoft.com`. Для мобильного DPI это
разные профили, поэтому начинать тест стоит именно с REALITY (RU).

## 5. Как пользоваться панелью и где брать ссылки подписки

### Вход

Панель: `https://<домен>:8444`. Порт **8444**, а не 443: на 443 висит только
подписка. Доступ к панели разрешён только с IP офиса (`ufw`), поэтому из другой
сети страница просто не откроется — это не поломка. Логин и пароль лежат в
`/opt/nsky/install-state.env` (`ADMIN_USER`, `ADMIN_PASS`, права 600). Пароль
светился в логе установки — смените его при первом входе и синхронизируйте в
state, иначе следующий запуск установщика не сможет войти.

Если IP офиса сменился (на NL-сервере):

```
ufw allow from <НОВЫЙ_IP> to any port 8444 proto tcp
ufw delete allow from <СТАРЫЙ_IP> to any port 8444 proto tcp
sed -i 's/^PANEL_ALLOW_FROM=.*/PANEL_ALLOW_FROM=<НОВЫЙ_IP>/' /opt/nsky/install-state.env
```

Последняя строка обязательна: иначе обновление установщика откатит правку.

### Что где лежит

| Раздел панели | Что там | Зачем трогать |
|---|---|---|
| **Home** | трафик, онлайн, статус нод | смотреть, подключился ли тестовый телефон |
| **Nodes** | нода `remnanode`, зелёная = подключена | если красная — `docker logs remnanode` |
| **Config Profiles** | профиль Xray, 3 инбаунда: 8443/tcp, 2053/tcp, 443/udp | не редактировать руками: установщик обновляет по тегам |
| **Internal Squads** | сквад `NSky` со ссылкой на инбаунды | новый инбаунд надо добавить сюда, иначе пользователи его не увидят |
| **Hosts** | 6 записей: 3 прямых + 3 `(RU)` | отсюда берутся адреса в подписке; `(RU)` = адрес русского VPS |
| **Users** | сотрудники, срок, лимит трафика и устройств | отсюда выдаётся ссылка подписки |
| **Settings → API Tokens** | доступ для второго админа | второй админ в панели невозможен (сидер удаляет лишних) |

### Получение ссылки подписки

1. **Users → Create user**: имя без пробелов, `Status = ACTIVE`, срок в
   *Access Settings*, обязательно выберите внутренний сквад `NSky`, при
   необходимости лимит устройств.
2. В строке пользователя нажмите **иконку ссылки** — она копирует Subscription
   URL. Альтернатива: карандаш → карточка пользователя, там же ссылка.
3. В меню пользователя есть **Subscription QR Code** (удобно для телефона) и
   **Subscription links** — «сырые» строки `vless://`, `hysteria2://` и т.д.
4. Откройте ссылку в браузере: должна появиться страница подписки с кнопками
   установки приложений. Это быстрая проверка, что всё настроено.
5. Передайте ссылку сотруднику (QR / мессенджер). Вставлять домен в приложение
   не нужно — адрес живёт только в ссылке.

Вид ссылки: `https://<домен>/<SUB_SECRET>/api/sub/<shortUuid>`. Сегмент
`<SUB_SECRET>` случайный и **секретный**: он прячет известный сканерам путь
`/api/sub` (сам `/api/sub` снаружи отдаёт 404). Не публикуйте ссылку в общих
каналах и не выкладывайте в репозиторий. Для тестового пользователя она также
лежит в `SUB_URL` файла `/opt/nsky/install-state.env`.

Все пользователи, привязанные к скваду `NSky`, автоматически получают **все**
хосты этого сквада — и прямые, и `(RU)`. Раздавать отдельную «мобильную» ссылку
не нужно: сотрудник просто выбирает сервер с пометкой `(RU)`.

### Обновление конфигурации

После смены настроек запускайте установщик **без** `--wipe`: пароли, UUID
инбаундов и нода сохраняются, хосты обновляются, `SUB_SECRET` берётся из state.
`--wipe` удаляет базу панели и меняет все ссылки — только для полной переустановки.

## 6. Известные ограничения текущего каскада

- Релей добавляет ещё один hop и NAT. Задержка выше, чем у прямого подключения;
  для Wi-Fi/стационарных сетей логичнее прямые серверы.
- `443/tcp` (подписка) и `8444/tcp` (панель) через релей не идут. Это описано в
  разделе 4.
- `nf_conntrack_udp_timeout_stream=120` для QUIC выставляется в
  `/opt/nsky-relay/apply.sh`, а не в `sysctl.d`; после перезагрузки его снова
  применяет systemd-юнит. Это нормально, но при ручной правке правил помните
  про этот параметр.
- `nsky-relay.sh --status` требует файл `/opt/nsky-relay/nl-ip`; без него он
  завершается с подсказкой. Новый чекер умеет работать с `--nl <IP>`.
- На русском VPS не должно быть своих сервисов на 8443/2053/`443/udp`: DNAT
  забрал бы их трафик. Чекер показывает слушающие порты.
- Второй администратор в Remnawave невозможен: используйте API-токен.
