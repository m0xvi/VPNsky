# Анализ, выбор стека и план

Дата анализа: **5 ноября 2026**. Все версии, лицензии и поведение протоколов проверены
в этот день по первоисточникам. Через 1–2 месяца часть выводов потребует перепроверки —
в РФ обстановка меняется быстро, а Xray/sing-box выпускают релизы раз в 1–2 недели.

## 1. Что обнаружено в репозитории и в архиве

Репозиторий `m0xvi/VPNsky` (private) на момент анализа содержал ровно один файл —
zip-архив передаточной записки прошлой сессии. Архив распакован в `docs/handoff/` без
изменений, контрольные суммы сошлись (кроме двух файлов, см. §8.6).

Суть архива, если коротко:

| Пункт | Состояние |
|---|---|
| Сервер | VPS Timeweb (`ams-1-vm-1ksc`), Xray VLESS+REALITY TCP/443 + отдельный `hysteria-server` UDP/443, nginx на `127.0.0.1:8443`, Telegram-бот, `/root/gen-subs.py`, watchdog |
| Аудитория | 41 активный клиент в Xray, ранее до 50+ сотрудников |
| Клиенты пользователей | Hiddify 4.1.1 (Android), v2rayNG — у обоих VLESS по TCP уходил в timeout по подписке и по прямому ключу; Hysteria2 поднимался, но YouTube/X работали через раз |
| Windows | Не проверялось вообще. SSH к VPS местами зависал на `SSH2_MSG_KEXINIT sent` |
| Код | Отсутствует полностью. GitHub Actions, релизы, control plane — не созданы |
| Лицензии | Помечены как «вопрос, требующий решения», вывод не сделан |
| Модель выдачи | Ссылка на 10 минут + подписка + общий пароль Hysteria2 — то есть **индивидуального отзыва клиента нет** |

Отдельно отмечу: **в архиве нет ни одного действия, которое нужно «отменить»**. Всё, что
в нём описано, — диагностика, заметки и предупреждения. Полезнее всего в нём список
грабель (не считать `systemctl active` работающим VPN, не путать 200 на сайте с доступностью
VLESS, не повторять патч `fix-xray-now.py`).

### Три вывода из архива, которые определяют архитектуру

1. **Проблема клиента №1 была не «сложный интерфейс», а сам туннель.** Hiddify/v2rayNG
   не подключались по VLESS. Любой новый красивый UI поверх неработающего туннеля даст тот же
   результат — только с более аккуратными сообщениями об ошибке. Следовательно, первый экран
   продукта — не UI, а воспроизведённое и проверенное соединение на реальной сети.
2. **Hysteria2 там был с общим паролем.** Значит, «отозвать» одного сотрудника технически
   невозможно — только выключить сервер или сменить пароль всем. Для управляемого продукта это
   блокер, а не улучшение.
3. **Подписка ≠ управление.** Подписка обновляет параметры подключения, но не меняет
   маршруты, kill switch, DNS и версию приложения. Нужен свой канал управления,
   а не «subscription URL».

## 2. Что выбрать серверной стороной

### 2.1. Data plane: Xray

**Рекомендация: Xray-core как единственное ядро и на сервере, и в клиенте.**

Проверено 05.11.2026 (Xray-core `v26.10.31`, MPL-2.0):

| Возможность | Подтверждение |
|---|---|
| VLESS + REALITY (TCP) | исторически «родной» сценарий Xray, у пользователя уже развёрнут |
| XHTTP-транспорт | есть в Xray, это основной ответ на детект длинных TLS-сессий |
| Hysteria2 **исходящий** (`protocol: "hysteria"`, `version: 2`) | есть в Xray с `v26.1.23`, транспорт `hysteriaSettings` + `finalmask.quicParams` (udphop, salamander) |
| TUN-инбаунд | с `v26.1.23`, с тех пор сильно доработан: Windows (Wintun), macOS, Linux, Android, iOS, FreeBSD |
| Блокировка утечек на Windows | `autoSystemWfpBlockLeak`: значения `dns`, `windnsclient`, `tcp/udp[/port]`, `icmp`, `misconfigtun`, `all`, `allexceptlan` — фильтры WFP, которые пускают мимо TUN только самого Xray |
| Автомаршруты и DNS | `autoSystemRoutingTable`, `autoSystemDnsToGateway` (Linux/FreeBSD), `dns` на адаптере Windows + сброс DNS-кеша |
| Управление пользователями в рантайме | gRPC API: `inbound_user_add`, `inbound_user_remove`, `inbound_user_count`, `stats_get_all_online_users`, `source_ip_block` и т.д. |
| Встраивание в мобильные приложения | `XTLS/libXray` (MIT, обёртка над Xray-core): сборка под Android (gomobile, min API 21), Apple (gomobile/cgo: iOS, macOS), Linux, Windows. Есть отдельный «desktop core» с флагами `-dns`, `-interface` для работы через elevation |

Почему это важно для вашей задачи: **одно ядро закрывает все три платформы и все три нужных
протокола**, включая Hysteria2. Не нужно тащить в продукт второе ядро, второй набор лицензий
и второй набор багов.

### 2.2. Почему не sing-box и почему это критично именно сейчас

sing-box — GPLv3 + запрет использовать имя/подразумевать ассоциацию без согласия. Для
**закрытого** продукта это означает: либо весь продукт открывается под GPLv3, либо
юридический риск. Karing (GPLv3) и Hiddify (GPLv3 + доп. условия, включая запрет
коммерческого использования без письменного согласия и требование публиковать форк) — тем более.

Отдельно: у sing-box **на 03.11.2026 открыт issue #4520** — sing-box вырезает
`X25519MLKEM768` из ClientHello, а Xray-core начиная с `v26.9.8` требует этот гибридный
пост-квантовый key share в REALITY, иначе молча уводит клиента на сайт маскировки. То есть
**свежий Xray-сервер и свежий sing-box-клиент несовместимы по REALITY прямо сейчас**.
С учётом того, что ваш VPS уже на Xray, «клиент на sing-box» — это гарантированная головная боль.
И ещё: с `v26.7.11` по `v26.7.28` Xray по умолчанию требовал клиента не старше `26.3.27`
(`minClientVer`) — вероятное объяснение старых таймаутов на Hiddify 4.1.1 из архива.
Это надо проверить на сервере, а не считать доказанным.

Для сравнения — лицензии (проверено по файлам в репозиториях):

| Компонент | Лицензия | Годится в закрытый продукт |
|---|---|---|
| Xray-core / libXray | **MPL-2.0** / MIT | **Да** (изменённые файлы MPL — опубликовать) |
| Hysteria2 (`HyNetworks/hysteria`) | **MIT** | **Да** |
| AmneziaWG (`amneziawg-go`) | MIT | Да, как отдельный модуль |
| hev-socks5-tunnel | MIT | Да |
| wintun (бинарь) | GPLv2 + отдельная лицензия на prebuilt `wintun.dll` | Да, при выполнении условий распространения рядом с продуктом |
| sing-box, Karing | GPLv3 (+ условия) | **Нет** без открытия |
| Hiddify | GPLv3 + NonCommercial + fork/Actions | **Нет** |
| 3x-ui / Marzban / Remnawave | GPL-3.0 / AGPL-3.0 | Нет как часть продукта; отдельный внутренний сервис — только после юридической оценки AGPL |

> Точные формулировки и оговорки — в [`ЛИЦЕНЗИИ_И_СООТВЕТСТВИЕ.md`](ЛИЦЕНЗИИ_И_СООТВЕТСТВИЕ.md).
> Это не юридическая консультация; перед публикацией продукта нужен юрист.

### 2.3. Control plane: свой сервис, а не панель

| Вариант | Лицензия | Пригодность |
|---|---|---|
| Свой сервис (Go) + gRPC Xray API + HTTP-auth Hysteria2 | ваш код | **рекомендую** |
| Remnawave | AGPL-3.0 | функционально близко, но AGPL и чужой роадмап; годится как источник идей |
| Marzban | AGPL-3.0 | то же |
| 3x-ui | GPL-3.0 | панель для админа-одиночки, не для продукта с 50+ устройств |

Ключевые аргументы за свой сервис:
- у вас уже есть 41 клиент и бот — миграция требует контроля, а не «панель перезапишет конфиг»;
- индивидуальные учётные данные на устройство + отзыв + аудит — это ~15 сущностей и 20 методов API,
  а не «ещё одна панель»;
- вы всё равно будете писать админское Android-приложение; ему нужен **ваш** API, а не веб-панель
  чужого проекта в WebView.

Серверные компоненты data plane при этом остаются штатными: `xray` (с API на loopback) и
`hysteria-server` (с `auth.type: http`, указывающим на ваш сервис).

## 3. Стек протоколов: что реально стабильно в РФ на ноябрь 2026

### 3.1. Состояние блокировок (сводка по публичным источникам, не по вашей сети)

- Массово и стабильно ломаются: OpenVPN, чистый WireGuard, IKEv2, Shadowsocks (энтропийный
  анализ), Trojan (по размеру пакетов).
- **17 февраля 2026** прошла волна блокировок VLESS+REALITY **по TCP** — жалобы на «заморозку»
  именно длинных TLS-сессий. Это ровно ваш сценарий (TCP/443). После этого сообщество
  переехало на XHTTP/мультиплексирование и на QUIC.
- Рабочими в 2026 называют три семейства: **VLESS+REALITY (лучше с XHTTP)**,
  **Hysteria2** и **AmneziaWG** (по AmneziaWG у Билайна с сентября 2026 — сообщения о блокировках).
- С сентября 2025 действует ст. 13.53 КоАП (поиск экстремистских материалов, 3–5 тыс. ₽),
  ст. 13.52 КоАП — для владельцев VPN-сервисов. Роскомнадзор в апреле 2026 публично подтвердил,
  что **корпоративные VPN внутри страны не ограничиваются**; компаниям с потребностью в доступе
  к зарубежным ресурсам предлагается подавать заявление и получать «белый список» IP.

> Это публикации профильных сайтов и новостей, а не измерения. Ваш собственный замер на
> Билайне (из архива) не подтверждал и не опровергал блокировку — там не было контрольного
> сравнения.

### 3.2. Рекомендуемый набор

| Приоритет | Транспорт | Зачем | Ограничения |
|---|---|---|---|
| **1** | VLESS + REALITY, TCP/443, XTLS-flow | максимальная совместимость и скорость, уже развёрнут | с февраля 2026 бывают «заморозки» длинных сессий |
| **2** | VLESS + XHTTP (+ REALITY), TCP/443 | тот же порт и SNI, но короткие HTTP-сессии; переживает атаку на длинные TLS | требует аккуратной настройки; в вашей версии Xray проверить на месте |
| **3** | Hysteria2, UDP/443 (+ salamander/gecko obfs, при необходимости port hopping) | лучший на lossy-сетях и мобильных, «второй, независимый по типу трафика канал» | UDP/443 режут на части сетей; Brutal нужно включать аккуратно (см. ниже) |
| опционально | AmneziaWG | ещё один независимый UDP-канал, полезен на Tele2/МТС | отдельное ядро → отдельная лицензионная и сборoчная история; только если реально понадобится |
| нет | OpenVPN, чистый WireGuard, Shadowsocks, Trojan | — | детектируются |

**Почему REALITY + XHTTP + Hysteria2, а не «один любимый протокол»:** ни один транспорт не
переживает все волны блокировок. Задача клиента — переключаться самому, а не заставлять
сотрудника звонить в поддержку. Три транспорта на двух типах трафика (TCP и UDP) — минимальный
набор, дающий независимость.

**Про Hysteria2 и Brutal.** В Hysteria2 (`app/v2.13.0`, MIT) сервер может выбрать
`ignoreClientBandwidth: true`, и тогда клиентские подсказки скорости игнорируются, а работают
local BBR/Reno. Для корпоративного сервера с 50+ людьми это **правильнее**, чем Brutal
(который «отжимает» полосу у остальных и требует точно указанной скорости у каждого клиента).
Значение `bandwidth` на сервере действует только на Brutal.

**Оговорка про автоопределение протокола.** Ни «умное переключение», ни «замер скорости»
не должны быть чёрным ящиком: клиент пробует канал, проверяет реальный ответ через туннель
(204/200 на доверенный endpoint), и только потом объявляет «Подключено». Иначе получится
ровно то, что было в архиве: «Hysteria2 подключился», а YouTube работает через раз.

## 4. Рекомендуемая архитектура

```
┌─────────── Сотрудник (Windows / Android / iOS) ───────────┐
│  Flutter UI  (только кнопка + статус + справка)           │
│      │                                                    │
│  Dart-мост (FFI/Platform channel)                         │
│      │                                                    │
│  Xray-core (libXray) ── TUN ── системные маршруты/DNS/WFP │
│      │  outbound: VLESS+REALITY / XHTTP / Hysteria2       │
│      └── TLS к control plane (не через туннель)           │
└───────────────────────────┬───────────────────────────────┘
                            │  HTTPS, токен устройства
┌───────────────────────────▼───────────────────────────────┐
│  Control plane (свой, Go) — на VPS или рядом              │
│   • устройства, политики, версии                          │
│   • выдача/ротация/отзыв учётных данных                   │
│   • gRPC → Xray API (add/remove user)                     │
│   • HTTP-auth эндпоинт → hysteria-server                   │
│   • аудит, Telegram-бот как UI                            │
└───────────────────────────┬───────────────────────────────┘
                            │ loopback
              ┌─────────────┴─────────────┐
        Xray (data plane)          hysteria-server
        VLESS REALITY / XHTTP       Hysteria2
```

### 4.1. Админское приложение: отдельный продукт, не «то же приложение с кнопкой»

Раз вы хотите админку на Android и Windows, а клиент тоже на Android и Windows, соблазн
сделать «одно приложение с ролями» велик. Технически это возможно (Flutter flavors +
разные capabilities), но:

- админское приложение не должно содержать VPN-ядро и TUN — ему туннель не нужен;
- у него другая модель угроз: украденный админский телефон = доступ ко всем устройствам;
- App Store/Google Play и MDM-распространение у них тоже разные.

Рекомендация: **одна кодовая база, две сборочные конфигурации**, физически разные пакеты
(`com.company.vpn` и `com.company.vpnadmin`), разные ключи подписи, разные API-скоупы.

### 4.2. Что именно автоматизируется для сотрудника

Это ответ на вашу главную боль («клиенты плохо ориентируются»):

1. Сотрудник получает ссылку-приглашение (одноразовый токен, TTL 10 минут) от админа.
2. Открывает приложение → «Активировать» → приложение само получает конфигурацию,
   поднимает TUN, выбирает первый рабочий транспорт и показывает одну кнопку.
3. Дальше **всё, что меняется на сервере** (новый SNI, новый порт, новый протокол, смена
   маршрутов, отзыв) приходит само. Приложение применяет атомарно: новая конфигурация
   проверяется локально и заменяет старую только если поднялась; иначе остаётся рабочая старая
   и в админке появляется «устройство X: конфигурация N не применилась».
4. Админ видит в приложении: кто онлайн, каким транспортом, версию клиента, сколько трафика,
   последняя ошибка (категорией, без секретов).

Ключевой принцип, который стоит зафиксировать сразу: **никаких исполняемых команд с сервера**.
Только декларативный документ конфигурации известной схемы + подпись.

| # | Вопрос | Почему важно | Как проверить |
|---|---|---|---|
| 1 | Работает ли REALITY с этим VPS из сети Билайн/МТС **сейчас** | Архив не дал ответа; февральская волна блокировок TCP | Поставить на VPS второй inbound на другом порту и прогнать с телефона; сравнить Xray-клиент vs v2rayNG на одной сети |

| 6 | iOS: Network Extension + paid Apple Developer | **без платного аккаунта VPN на iPhone не собрать** (проверено) | Оформить membership до старта iOS-этапа |
| 7 | Совместимость версий Xray-сервер ↔ Xray-клиент | `minClientVer` и требование `X25519MLKEM768` с `v26.9.8` уже ломали клиентов | Зафиксировать версию сервера; клиент обновляется вместе с сервером |
| 8 | Поведение `xray` под нагрузкой 50+ клиентов | один VPS — одна точка отказа | Отдельный нагрузочный прогон, не раньше пилота |

### 5.1. Важное следствие для iOS

В архиве записано «лицензия не нужна, ставим через кабель». Это **неверно** в части
возможностей: туннель на iOS требует entitlement `packet-tunnel-provider`, который Apple
выдаёт только участникам **платной** программы разработчиков ($99/год). Бесплатный аккаунт
и re-signing-утилиты (AltStore, Sideloadly) его не дают: приложение можно подписать, но VPN
не запустится. Также на iOS нельзя ставить сторонние сборки «навсегда» — профиль
разработчика живёт ограниченное время, если не используется MDM/TestFlight/App Store.

Значит: iOS-этап требует Apple Developer Program **и** решения, как обновлять приложение у
сотрудников (MDM или TestFlight). Это организационный вопрос, его лучше закрыть сейчас,
пока iOS не начат.

| **2. Ядро клиента** | Библиотека-обёртка над Xray (`libXray`) + загрузка конфигурации + TUN | На Windows 10/11: включается кнопкой, весь трафик идёт через туннель, DNS не течёт, есть kill switch-политика |
| **3. Control plane MVP** | Go-сервис: устройства, токены, выдача конфигурации, отзыв, аудит | Новое устройство активируется за <2 минут, отзыв проверен (сессия рвётся), Xray-пользователь удаляется |
| **4. UI Windows** | Один экран, состояния, диагностика, автообновление | Сотрудник без инструкции подключается с первого раза |
| **5. Админка** | Windows/Android: список устройств, действия, статус | Админ с телефона выдаёт доступ и отзывает его |
| **6. Пилот** | 5–10 сотрудников, разные сети | Собираются метрики успешных подключений, есть откат |
| **7. Android** | Продукт для сотрудников | VpnService, kill switch, автообновление |
| **8. iOS** | Продукт для сотрудников | Network Extension, MDM/TestFlight |

Порядок «Windows → Android» из архива сохраняю: на Windows вы отлаживаете ядро и конфигурацию
без платформенной магии, и это дешевле, чем искать причину таймаута сразу на телефоне.

## 7. Открытые вопросы (нужны ответы, чтобы не гадать)

Блокирующие для этапа 1:

1. **Сервер.** Остаёмся на текущем VPS (тогда — второй набор портов и полный бэкап перед
   любым изменением) или поднимаем отдельный тестовый VPS под разработку?
   Рекомендация: **отдельный** — текущий обслуживает людей, и любые эксперименты на нём

3. **Кто пользователи.** 50+ сотрудников одной компании, или планируется несколько компаний?
   Второе резко меняет модель данных и биллинг (и вообще требует лицензионной проверки).

Позже, но до этапа 5:

5. Админка: только Android + Windows, или нужен веб? Если веб, то это ещё один UI-слой.

8. Apple: есть ли уже Apple Developer Program, планируется ли MDM?

## 8. Замечания по качеству исходных данных

1. **Даты.** Часть выводов архива («41 клиент», «Hiddify 4.1.1 timeout») — снимок прошлых
   сессий. Актуальность неизвестна.
2. **«Пользователь видел timeout» — не диагноз.** Ни версия Xray на сервере, ни `minClientVer`,
   ни REALITY key share тогда не сверялись. Сегодняшние публичные отчёты дают правдоподобную
   версию (см. §2.2), но её нужно подтвердить на стенде.
3. **iOS-лицензия.** Утверждение «лицензия не нужна» в архиве относится к лицензии на ПО,
   но не к Apple Developer Program. Это разные вещи, и вторая — платная.
4. **`SHA256SUMS.txt` в архиве не сходится для двух файлов** (`00_...`, `01_...`).
   Причина — предыдущая сессия пересохраняла эти два файла после расчёта сумм; на содержимое
   это не влияет (тексты читаемы, дублей нет), но формально целостность архива в этой части
   не подтверждена. Файлы сохранены как есть.
5. **В архиве есть IP, домен и внутренняя топология VPS.** Репозиторий приватный — это
   минимизирует риск, но в `docs/handoff/` эти данные остаются. Если репозиторий когда-либо
   станет публичным или в него добавятся подрядчики — сначала вычистить. Рекомендую также
   убрать из будущих документов реальный IP и заменить на placeholder.
6. **Утверждения о блокировках** в §3.1 — из публикаций, не из вашей сети. Не основание
   для выводов о причинах прошлых сбоев.
