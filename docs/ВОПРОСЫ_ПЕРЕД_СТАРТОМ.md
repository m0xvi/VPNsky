# Что уточнить перед стартом работ над приложениями

Дата: **5 ноября 2026**. Документ отвечает на два вопроса: (1) реализуем ли ваш сценарий
«сервер недоступен → клиент получает уведомление», (2) какие детали нужно зафиксировать,
чтобы не переделывать.

---

## 1. Разбор вашего сценария

Вы описали: клиент не пингует сервер → клиент получает уведомление
«VPN-сервер недоступен, проблема на стороне провайдера».

### 1.1. Технически это два разных события, и их нельзя путать

| Что произошло | Кто это видит | Как узнать |
|---|---|---|
| **Панель потеряла связь с нодой** | панель | штатный webhook Remnawave `node.connection_lost` (проверено, есть в документации) |
| **Клиент не может достучаться до ноды** | клиент (и только он) | приложение само пробует подключиться и не может |
| **Клиент не может достучаться до панели/подписки** | клиент | запрос подписки не проходит |
| **Нода жива, но конкретный протокол режут** (ТСПУ) | клиент | TCP/443 проходит, а соединение не устанавливается |

Это **разные** отказы. Нода может быть недоступна из сети Билайн, но прекрасно видна
из панели на другом хосте. И наоборот: панель не видит ноду, а клиенты ещё подключены и
работают (установленные сессии живут).

### 1.2. Что из этого можно сделать на готовом клиенте

| Возможность | Реально? | Как |
|---|---|---|
| Клиент сам показывает «сервер недоступен» | **Да, но текстом приложения** | Happ показывает ошибку подключения своим текстом. Переформулировать под нас нельзя |
| Наш текст «проблема на стороне провайдера» в момент сбоя | **Нет** | Текст можно передать только через `announce` **внутри подписки**, а подписка в этот момент может быть недоступна |
| Наш текст, который увидит сотрудник **после** восстановления («был сбой, всё работает») | **Да** | `announce` меняется на сервере → приложение получает его при следующем обновлении подписки |
| Мгновенный push в приложение | **Нет** (без своего клиента) | см. `УВЕДОМЛЕНИЯ.md` |
| Админ мгновенно узнаёт о падении ноды | **Да** | webhook `node.connection_lost` → уведомление в канал админа |

### 1.3. Отдельно: формулировка «проблема на стороне провайдера» — опасная

Мы **не знаем**, чей это провайдер. Варианты: хостинг ноды, оператор сотрудника (МТС/Билайн
режут), ТСПУ, авария на магистрали. Если написать «виноват провайдер», а окажется, что упал
наш сервер — выглядит как перекладывание ответственности. Если у сотрудника плохой Wi-Fi —
тоже неловко.

Что предлагаю вместо этого (можно выбрать):

| Вариант текста | Когда уместен |
|---|---|
| «Сервер временно недоступен. Пробуем другой» | нейтрально, всегда честно |
| «Нет связи с сервером. Проверьте интернет и попробуйте снова» | когда часть пользователей работает, а часть нет |
| «Работаем над восстановлением. Статус: status.домен.ру» | когда инцидент подтверждён админом |

Важно: **это вопросы формулировок и процесса, а не кода** — и решать их надо до того,
как писать тексты в приложении.

### 1.4. Что я рекомендую сделать вместо «уведомления о недоступности»

Три вещи по возрастанию сложности:

1. **Автоперебор серверов в клиенте.** У нас будет ≥2 транспорта (REALITY, Hysteria2) и
   возможность добавить вторую ноду. Клиент при неудаче переключается сам, а не показывает
   «недоступен». Это закрывает 80% вашего сценария без всяких уведомлений.
2. **Страница статуса + `announce`.** Админ при инциденте меняет одну строку в панели.
3. **Мониторинг с алертом админу.** Чтобы «уведомлять» было о чём — сначала надо узнать.

## 2. Какие приложения вообще пишем

Первый вопрос, который надо закрыть, потому что от него зависит всё остальное:

**Вариант A.** Пишем **только админское** приложение (Android/Windows), клиент — готовый
(Happ). Сроки: недели. Объём: UI к API панели.
**Вариант B.** Пишем **свой клиент** сотрудника (Windows/Android/iOS) + админку. Сроки: месяцы.
Объём: ядро, TUN на трёх платформах, kill switch, автообновление, подпись, магазины.
**Вариант C.** Сначала A, через полгода — B.

Мой дефолт: **C**. Причины: клиент уже работает, а всё, что вы хотите «своё» (тексты, экраны,
уведомления), без своего клиента не сделать — но и начинать с трёх платформ дорого.

Дальше вопросы разбиты по блокам. Где можно — указан мой дефолт, чтобы можно было просто
согласиться.

## 12. Что блокирует старт (без этого не начинаем)

| # | Вопрос | Почему блокирует |
|---|---|---|
| 12.1 | **Вариант A/B/C из §2** — что пишем | определяет весь объём |
| 12.2 | Домены и серверы | без них нет ни панели, ни тестов |
| 12.3 | Страна ноды | без неё нельзя проверить протоколы |
| 12.4 | Сплит или полный туннель (§6.1) | закладывается в профиль Xray |
| 12.5 | Тексты сообщений при сбое (§7.4) | попадают в UI и в `announce` |
| 12.6 | Есть ли канал гарантированного оповещения сотрудников (§8.2) | определяет, обещать ли «сотрудник точно узнает» |
| 12.7 | Кто админы и сколько | доступы, роли, 2FA |

Остальное можно решать по ходу — но лучше зафиксировать в одном месте, чтобы не
переспрашивать на каждом шаге.
