# Билайн: что сделать прямо сейчас

Одна страница. Обновлено по результатам первой живой проверки.
**Цель:** телефон на LTE Билайн открывает `2ip.ru` и видит IP Нидерландов.

## Что делать прямо сейчас (по последнему выводу)

### Что уже хорошо

- **Автозапуск пережил перезагрузку**: `--relay` на RU дал 13 ok / 0, все
  8 правил на месте. Это та проверка, которую мы откладывали, — она пройдена.
- NL после reboot: `HTTP 200`, все порты слушаются, TLS и UDP-пробы зелёные.
- Ротация `SUB_SECRET` прошла успешно: Caddy, `.env` панели и state согласованы.
- `udp dpt:443` на релее = **36 пакетов / 46 КБ** — это уже не 10-байтовые
  пробы чекера, а реальный QUIC-обмен с телефона. Значит, Билайн **не блокирует**
  ни IP русского VPS, ни UDP/443. Hysteria2 доходит до релея, но handshake
  не завершается и `1.1.1.1/cdn-cgi/trace` не открывается.

### В чём поломка

**«План Б» применён наполовину.** В панели у `NSky REALITY (RU)` стоит порт
**443/tcp**, а на релее в `PREROUTING` только три правила: `8443/tcp`,
`2053/tcp`, `443/udp`. Правила `tcp/443 → NL:8443` **нет** (оно было временным
и исчезло при перезагрузке). Поэтому REALITY (RU) сейчас указывает в пустоту.

При этом старый чекер показывал `✓ REALITY (RU): TLS дошло` — **ложная
галочка**: он проверял жёстко заданный `RU_IP:8443`, а телефон ходил на `:443`.
Исправлено в **v2026-11-06.4**: порт теперь берётся из подписки, а `443/tcp`
у `(RU)` даёт честное предупреждение «план Б: нужен DNAT tcp/443».
У вас на NL запускается **v.2** — его надо скачать заново.

**Ещё два важных последствия ваших действий:**

- `reset-superadmin` выполнен **дважды**, после второго сразу `reboot`.
  Нового админа не зарегистрировали → сейчас в панели **нет администратора**.
  Откройте `https://<домен>:8444`, зарегистрируйте супер-админа заново, затем
  через `nano` синхронизируйте `ADMIN_USER`/`ADMIN_PASS` в
  `/opt/nsky/install-state.env`. Пользователи, хосты, нода и API-токены
  сбросом не задеты.
- Ротация `SUB_SECRET` сделала **все старые ссылки подписки недействительными**.
  Берите новую из панели (Users → иконка ссылки).

### Четыре шага

**Шаг 1. Машина B (RU), одна строка** — доделать план Б:

```
iptables -t nat -A PREROUTING -p tcp --dport 443 -j DNAT --to-destination $(cat /opt/nsky-relay/nl-ip):8443
```

Проверка отдельной строкой — должна появиться запись с `--dport 443` и
`--to-destination …:8443`:

```
iptables -t nat -S PREROUTING | grep 'dport 443'
```

Вставлять строго по одной строке, Enter после каждой. При мусоре вprompt —
`Ctrl+C` и повторить. Правило **временное**: не перезагружайте RU до проверки;
когда заработает, добавим его в `apply.sh`, чтобы переживало reboot.

**Шаг 2. Машина A (NL), две строки** — обновить чекер (у вас v.2):

```
curl -fsSL -o /root/nsky-cascade-check.sh https://raw.githubusercontent.com/m0xvi/VPNsky/6fd030edb1285fe58fb5ce8cfea5abda045705f9/deploy/nsky-cascade-check.sh
bash /root/nsky-cascade-check.sh
```

Ждём `v2026-11-06.4`, предупреждение `! план Б: … нужен DNAT tcp/443`,
`✓ REALITY (RU) [:443]: TLS-рукопожатие дошло до ноды` и **0 ошибок**. Если
вместо этого `✗ REALITY (RU) [:443]: … не работает DNAT` — значит шаг 1 не
выполнился, повторите его.

**Шаг 3. Машина D** — зарегистрировать администратора в панели (см. выше) и
синхронизировать state.

**Шаг 4. Машина C** — по Wi-Fi обновить подписку **новой ссылкой** (после
ротации), выключить Wi-Fi, на LTE Билайн вручную выбрать
**`NSky REALITY (RU)`**, подключить и открыть:

```
https://1.1.1.1/cdn-cgi/trace
```

Если REALITY (RU) не заработает — следующим попробовать
**`NSky XHTTP (RU)`** (2053/tcp, DNAT точно есть). Результат `NSky Hysteria2
(RU)` уже известен: пакеты доходят, handshake нет.

> `inactive` у `nsky-relay.service` в старом выводе — норма для oneshot с
> `RemainAfterExit=yes`. `ufw inactive` при `-P FORWARD ACCEPT` — тоже норма.

## Если Happ пишет «Тайм-аут» при добавлении или обновлении подписки

**Это ожидаемо на LTE Билайн и не означает поломки серверов.**

Ссылка подписки ведёт на зарубежный домен, `443/tcp` нидерландского сервера.
Релей пробрасывает только `8443/tcp`, `2053/tcp` и `443/udp`; **`443/tcp`**
(подписка) и **`8444/tcp`** (панель) через него не идут. Happ при добавлении
ссылки делает обычный HTTPS-запрос напрямую, Билайн его режет, клиент не
дожидается ответа и показывает «Тайм-аут».

**Это не провайдер VPS и не авария.** По уже присланным логам:

| Проверка | Что показала |
|---|---|
| `nsky-cascade-check.sh --relay` на RU | 13 ok / 0 ошибок, правила и автозапуск на месте |
| Счётчик `tcp dpt:8443` на релее | Рос при подключении телефона → входящие порты провайдером не закрыты |
| Панель, тестовый пользователь | Трафик и «Последняя нода `nsky-node-1`» → NL-нода жива |
| Чекер на NL | `HTTP 200` на публичную ссылку → подписка на сервере отдаётся |

Если бы хостинг блокировал порты, счётчики DNAT не росли бы. Разница простая:
**туннель** идёт через релей и работает, а **запрос на обновление подписки**
идёт мимо релея и потому не проходит.

Что делать:

1. **Не добавлять и не обновлять подписку по LTE.** Закрыть окно с таймаутом.
2. Если карточка с 6 серверами ещё есть — просто выбрать `NSky Hysteria2 (RU)`
   и подключить. Обновление **не требуется**: конфиг на сервере не менялся,
   кэш подписки действителен.
3. Если карточка удалена — добавить ссылку **один раз из другой сети**
   (домашний Wi-Fi, точка доступа от другого оператора), затем вернуться на LTE.
4. Если другой сети нет: в панели (машина D) `Users → карандаш → More actions
   → Subscription links` взять «сырую» строку `hysteria2://` для хоста `(RU)`
   и добавить её в Happ вручную через «+» / «из буфера» / QR. Такой профиль
   не делает запрос к зарубежному домену и таймаута не даёт.

> Проксировать `443/tcp` подписки через русский VPS технически можно, но это
> отдельная доработка, и она **конфликтует с планом Б** (тот же порт `443/tcp`).
> Не начинайте её, пока не проверено само подключение.

## Что прислать, если не заработало

Без доменов, IP, паролей и ссылок:

1. Вывод нового чекера v.4 на NL: есть ли `✓ REALITY (RU) [:443]` и сколько ошибок.
2. Какой `(RU)`-сервер выбран на телефоне и что показал
   `https://1.1.1.1/cdn-cgi/trace`.
3. Счётчики `PREROUTING` на релее после попытки: растут ли `tcp dpt:443` и
   `udp dpt:443`.
4. Удалось ли зарегистрировать администратора заново.
