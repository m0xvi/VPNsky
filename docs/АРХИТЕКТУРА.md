# Архитектура

Документ описывает целевую архитектуру. Технические решения по протоколам и лицензиям
обоснованы в [`АНАЛИЗ_И_ПЛАН.md`](АНАЛИЗ_И_ПЛАН.md).

---

## 1. Компоненты

| Компонент | Технология | Лицензия | Платформы |
|---|---|---|---|
| Клиент сотрудника | Flutter + Xray-core через `libXray` | ваш код + MPL-2.0/MIT | Windows 10/11 x64, Android 8+, iOS 16+ |
| Админское приложение | Flutter (тот же репозиторий, второй flavor) | ваш код | Android, Windows |
| Библиотека-обёртка ядра | Dart FFI + тонкий Go/сишный слой над `libXray` | ваш код | общая |
| Control plane | Go (HTTP/JSON, gRPC-клиент к Xray) | ваш код | Linux |
| Data plane | `xray` + `hysteria-server` | MPL-2.0 / MIT | Linux |
| Хранилище | PostgreSQL (или SQLite для стенда) | — | — |
| Бот | Go/Node, тонкий клиент к API control plane | ваш код | — |

Правило: **всё, что знает о протоколах, — только ядро**. В UI нет ни UUID, ни ключей, ни
портов. UI оперирует состояниями: `IDLE → CONNECTING → CONNECTED → RECONNECTING → BLOCKED →
NEEDS_ADMIN`.

## 2. Потоки данных

### 2.1. Активация устройства

```
Админка ──(create device)──► Control plane ──► БД + Xray API (add user) + Hysteria auth entry
                                    │
                                    └──► одноразовый код (TTL 10 мин, хэш в БД)
Сотрудник вводит код / открывает deeplink
      │
      ▼
Клиент ──HTTPS──► POST /v1/activate {code, device_pubkey?}
      │            (TLS pinning, отказ при неверном сертификате)
      ▼
Control plane ──► проверяет код атомарно (used_at), создаёт device_token,
                  отдаёт подписанный документ конфигурации
```

Требования:
- код одноразовый; повторная активация — только через админку;
- `device_token` — 32+ байта, хранится в Windows Credential Manager / Android Keystore /
  iOS Keychain;
- конфигурация подписывается ключом, публичная часть вшита в приложение (Ed25519).
  Приложение проверяет подпись **до** применения. Ключ подписи ротируется, старые
  конфигурации остаются валидными до истечения.

### 2.2. Получение и применение конфигурации

```
Клиент (раз в N минут + при старте + при ошибке)
      │  GET /v1/config  (Authorization: Bearer)
      ▼
Документ:
{
  "schema": 3,
  "revision": 42,
  "expires_at": "...",
  "profile": {
    "transports": [            // порядок = приоритет
      {"kind":"vless-reality","host":"vpn.example.com","port":443,
       "uuid":"...","flow":"xtls-rprx-vision","sni":"...","pbk":"...","sid":"..."},
      {"kind":"vless-xhttp","host":"vpn.example.com","port":443,"path":"/xyz",...},
      {"kind":"hysteria2","host":"vpn.example.com","port":443,"password":"...","obfs":null}
    ],
    "policy": {"mode":"full|split","kill_switch":true,"dns":"tunnel","ipv6":"disable|tunnel"}
  },
  "signature": "..."
}
```

Правила применения:
1. Проверить `schema` (неизвестная — не применять, оставить старое).
2. Проверить подпись.
3. Сконвертировать в конфиг Xray, валидировать локально (`xray run -test` или API валидации).
4. Запустить новый туннель в отдельном процессе/инстансе.
5. Проверить реальный запрос через туннель (доверенный endpoint).
6. Только после успеха — переключить маршруты на новый и удалить старый; сохранить как
   «последняя рабочая».
7. При любом провале — откат к сохранённой конфигурации, отчёт в control plane
   (`config_apply_failed`, revision N, категория ошибки).

### 2.3. Проверка соединения и автопереключение

- «Подключено» показывается **только** после успешного контрольного запроса через туннель.
- Проверка идёт по HTTPS к вашему же эндпоинту (`/v1/ping`, ответ 204), а не к внешнему
  сайту: не зависим от блокировок целевого ресурса и не утекаем запросами.
- Порог переключения: 2 подряд неудачи с интервалом 5–10 с → переход на следующий транспорт
  с экспоненциальным backoff (5 с → 10 → 30 → 60 → 120 с, потолок).
- Антифлап: не более 5 переключений за 10 минут, затем «BLOCKED — ждите обновления
  конфигурации» + отправка телеметрии. Без этого получим батарееед и «моргающий» статус.
- После успешного переключения — не возвращаемся к предыдущему транспорту сразу: возврат
  только по таймеру (например, проверка раз в 30 минут) и только если он реально работает.

## 3. Серверная часть

### 3.1. Размещение

- Control plane: один сервис, слушает `127.0.0.1:8000` за nginx (TLS 1.3, HSTS), доступ
  из интернета только к `/v1/activate`, `/v1/config`, `/v1/ping`, `/v1/report`, `/api/admin/*`.
- Админский API: отдельный путь + отдельная аутентификация (Telegram user_id + device token
  админского приложения), отдельный rate limit.
- Xray API: только `127.0.0.1:10085`, доступ — mTLS или unix socket.
- hysteria-server: `auth.type: http` → `http://127.0.0.1:8000/internal/hysteria-auth`.
  Проверено по документации Hysteria 2: сервер шлёт POST `{addr, auth, tx}`, ожидает
  `200 {"ok":true,"id":"..."}`. Это даёт индивидуальный отзыв без смены общего пароля.

### 3.2. Схема данных (минимум)

```
users(id, display_name, status, created_at)
devices(id, user_id, platform, os_version, app_version, status,
        token_hash, token_rotated_at, last_seen_at, last_transport, last_error_code)
vpn_credentials(id, device_id, kind, secret_encrypted, created_at, revoked_at)
  -- отдельная запись на каждый транспорт
configs(id, user_id, revision, payload_json, signature, valid_from, valid_until)
activation_codes(id, device_id, code_hash, expires_at, used_at)
admin_audit(id, admin_tg_id, action, target_id, result, at, ip_hash)
metrics(device_id, day, bytes_up, bytes_down, transport)  -- агрегаты, не по сайтам
```

Что **не** храним: историю доменов, содержимое трафика, полные конфиги в логах, IP клиентов
в открытом виде (только хэш для антифрода, если понадобится).

### 3.3. Отзыв

Отзыв — две независимые операции, и обе должны быть реализованы:

1. **Серверный доступ**: `inbound_user_remove` в Xray API + удаление записи в
   hysteria-auth → новые подключения невозможны сразу, установленные рвутся перезапуском
   транспорта/по таймауту.
2. **Клиентский доступ**: `revoked_at` в `devices` → `/v1/config` отдаёт 401 → приложение
   переходит в `NEEDS_ADMIN` и не пытается подключаться.

Если сделать только (2), скопированный конфиг продолжит работать. Если только (1) —
приложение будет висеть в «Подключаемся».

### 3.4. Аудит и логи

- Пишем: действие, псевдоним устройства, результат, категорию ошибки, время.
- Не пишем: UUID, пароли, ссылки, SNI/домены посещений, IP, query string.
- Логи приложения не отправляются «целиком» — только фиксированный словарь кодов
  (`tun_start_failed`, `handshake_timeout`, `dns_failed`, `config_invalid`).

## 4. Клиент: платформенные детали

### 4.1. Windows

- `xray.exe` (собранный из `XTLS/Xray-core` вашим CI) + `wintun.dll`.
- TUN-инбаунд Xray с `autoSystemRoutingTable: ["0.0.0.0/0","::/0"]`,
  `autoOutboundsInterface: "auto"`, `autoSystemWfpBlockLeak: ["dns","misconfigured..."]`
  (точные значения — по документации `proxy/tun/README.md`).
- Служба Windows (LocalSystem) для создания TUN и WFP-фильтров + UI без прав администратора.
  UI общается со службой через named pipe с проверкой SID вызывающего.
- **Не** полагаться на системный прокси: половина приложений его игнорирует.
- Удаление: служба, адаптер `xray0`, маршруты, WFP-фильтры — всё должно убираться
  при деинсталляции (это отдельный тест-кейс).

### 4.2. Android

- `VpnService` создаёт TUN, fd передаётся в Xray через `xray.tun.fd`/`XRAY_TUN_FD`.
- `libXray` собирается gomobile (min API 21). Готовый AAR подключается к Flutter-плагину.
- Always-on VPN + «Блокировать соединения без VPN» настраиваются через device policy/MDM
  либо вручную с инструкцией; программно включить нельзя без прав device owner.
- Учитывать battery restrictions: foreground service + уведомление обязательно.

### 4.3. iOS

- Network Extension (`packet-tunnel-provider`), `libXray` собранный под iOS (gomobile/cgo).
- Требуется платный Apple Developer Program; бесплатный аккаунт entitlement не даёт.
- Распространение: TestFlight (до 10 000 внешних тестеров, ревью обязательно) или MDM.
  «Поставить по кабелю на каждое устройство» работает, но профиль живёт ограниченное время
  и обновлять так 50+ устройств нереально.
- Правило App Store 5.4: VPN-приложение требует организации-разработчика; для внутреннего
  корпоративного использования есть Apple Business Manager / custom apps.

## 5. Модель угроз (кратко)

| Угроза | Мера |
|---|---|
| Украден токен устройства | короткий TTL + ротация, привязка к платформе, отзыв в один клик, аудит |
| Украден админский телефон | отдельный API-скоуп, подтверждение действий (Telegram 2FA), отдельная подпись сборки |
| Подмена конфигурации | подпись Ed25519, TLS pinning, отказ при несоответствии |
| Компрометация control plane | секреты VPN шифруются ключом из KMS/локального файла, БД без открытых секретов |
| Утечка при падении туннеля | kill switch (WFP на Windows, `always-on` на Android), проверено в тестах |
| Утечка через DNS | DNS только внутри TUN, `autoSystemWfpBlockLeak: dns` |
| Ретроспектива трафика | не логируем домены/IP, храним только агрегаты |
| Insider в support | доступ к админке по ролям, все действия в аудите |
| Один VPS упал | второй сервер и failover-конфигурация (этап после пилота) |

Ограничения, которые не закрываются ничем:
- копия конфигурации с устройства работает до отзыва — аппаратной привязки нет;
- блокировку IP сервера нельзя «обойти протоколом», только сменой адреса;
- подпись конфигурации защищает от подмены, но не скрывает содержимое на устройстве.

## 6. Совместимость версий (жёсткое правило)

С `v26.9.8` Xray-сервер требует у REALITY-клиента гибридный `X25519MLKEM768` key share,
а ранее (в `v26.7.11`–`v26.7.28`) по умолчанию требовал клиента не старше `26.3.27`.
Это уже ломало сторонние клиенты.

Поэтому:
- версия Xray **фиксируется** в одном месте (`versions.env`), сервер и клиент обновляются
  только вместе, через проверенный релиз;
- клиент старой версии должен получать от control plane **конфигурацию под свою версию**
  (поле `min_client_version` в документе) и явное сообщение «обновите приложение»,
  а не молчаливый таймаут;
- в CI — тест совместимости: собранный клиент против стендового сервера той же версии.
